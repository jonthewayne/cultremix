# Image generation

How CultRemix makes designs, what each call costs, and how the pieces fit: the studio's images and style mixer, the notes written for every image, the four-up grid, upscaling for print, and what the printers need. Measured on the gateway between 2026-09-29 and 2026-09-30; the scripts live in `~/cultremix-imagecheck/` on mighteous.

The history behind the studio's style handling, with every style test in date order, the ways of mixing styles we compared, and what's still open, is in [Styles and mixing](style-mixing.md).

## Models

All image calls go through the Vercel AI Gateway with AI SDK 7 `generateImage`, `maxRetries: 0`.

| Job | Model |
|---|---|
| A design from words only | `openai/gpt-image-2.5-flare` |
| Anything with an input image: the studio's images, style images, remixes, model photos | `openai/gpt-image-2.5-sunburst` |
| Notes for an image (what's in it, how it looks) | `openai/gpt-6-luna`, reasoning effort low |
| What a request wants from each image, and whether it asks for the style's hair | `openai/gpt-6-luna`, reasoning effort low |
| How far a remix moved from its original (variation or fork) | `openai/gpt-6-luna`, reasoning effort low |
| Upscale for print | fal `topaz/upscale/image/transparent` |

Dev normally uses Jon's ChatGPT login (`CHATGPT_ACCESS_TOKEN`), which runs a different image model. Set `IMAGE_PROVIDER=gateway` on dev to test with the production models.

The model names live in `convex/lib/models.ts`. The image test suite (`tests/image-e2e`, `bun run test:image`) reruns every capability below against them; try a new model there before changing that file.

### Other models, for admins

Admins at the "manage" level (owner and ops) see a **Model** picker beside Generate; members always get GPT Image 2.5, and the server refuses another model from anyone else. Each design shows its model's name, and so does its batch line.

| Choice | How a batch is made | Credits | Measured 2026-10-06 |
|---|---|---|---|
| GPT Image 2.5 | One 2x2 grid call, transparent, cut into four | 2 | about 10-11¢ at high |
| Nano Banana 2.1 (`google/gemini-nano-banana-2.1`) | One 2x2 grid call at 2048x2048 on a flat key color, keyed out, then cut | 2 | 5.9-6.6¢ a call; 22 s from words, 26-31 s with an image |
| Recraft V4.1 (`recraft/recraft-v4.1`) | Four 1024x1024 calls, each asking for a transparent background | 4 | 3.5¢ and 8-18 s each |
| Mix of all three | Four separate calls: two GPT Image 2.5 at the grid's quality, one Nano Banana 2.1, one Recraft V4.1 | 4 | about 30¢ |

- **Nano Banana 2.1 can't make a transparent background.** It returns an opaque JPEG; asked for transparency, it painted the background black. Its prompt asks for a flat magenta background instead (green when the prompt leans pink or purple, `keyFor`), and `convex/lib/chromaKey.ts` clears it: the background connected to the image's edge, background showing through holes in the artwork (inside letters, between a crown's points), and the key color mixed into soft edges, so a pencil sketch's gray lines stay gray instead of turning pink. The key color is measured from the image's edge, since the model's magenta isn't always pure: one design's was (254, 27, 254), which left a faint pink panel when the keyer assumed (255, 0, 255). Keying is free and takes about a second, so no second call is needed to remove the background. Shading the model draws as part of the art (a soft gray halo behind a sketch) stays.
- **Recraft V4.1 takes words only** through the gateway, and only 1024x1024 (1024x1536, 1024x1280, 2048x2048, and others were refused). Its prompt says the images aren't attached and lets their notes stand in, without naming a style image's own subjects or describing its figures (with them, it drew the style images' woman and picnickers). Requests that work from an image suffer most: for "Change the lion to a wolf" on the lion sketch, two of four Recraft designs drew a lion.
- **First comparison** (the lion sketch, "Change the lion to a wolf", one batch each): Nano Banana kept the sketch look, the arched hand lettering, and the composition in four of four wolves; GPT Image 2.5 did the same in its two; Recraft drew two wolves and two lions in its own cleaner sketch style. Sheets: `.tmp/shots/b2-three.png`, `.tmp/models/sheet1.png`, `.tmp/models/sheet2.png`.
- The daily budget reserves each choice's own worst case: 12¢ for a Nano Banana call and 5¢ for a Recraft call, plus 1¢ for reading the request (`convex/lib/pricing.ts`). The roles reader and the notes run as they do for GPT Image 2.5.

Quality changes detail, not size: a high grid is the same 1920×1920 with more detail in fur, faces, and texture; bold lettering looks almost the same. With quality unset the model picked high for four of five grids. High looks clearly better on illustrations, so the grid should default to high: about 10–11¢ per batch of four, which suggests 2 credits per batch (about 5¢ of image cost per credit).

The studio makes each batch as one grid at high quality (`GRID_QUALITY`, default `high`): about 10–11¢ of image cost for four designs, charged 2 credits. Single designs (the ChatGPT path, or `STUDIO_LAYOUT=single`) and model photos use `IMAGE_QUALITY` and `PHOTO_QUALITY` (default `medium`). A grid also reads each input image once per batch instead of four times.

## The four-up grid

One call makes four designs in a 2×2 grid; `convex/lib/gridCut.ts` cuts them apart. A grid gives more varied designs than four separate calls (which came back nearly identical) and costs less at medium.

**Size.** GPT Image 2.5 sizes must have both sides a multiple of 16 px, at most 3,686,400 px in total, a long side at most 3× the short side, and no side over 3,840 px; larger sizes are experimental. The largest non-experimental square is **1920×1920**, and that's the grid size. The tall 1536×2304 grid didn't help. Each cut design comes out about 730–900 px wide and 800–940 px tall.

**Prompt.** `GRID_RULES` in `convex/lib/prompts.ts` asks for one complete graphic centered in each quarter, about 80% of its quarter, with wide empty space between them, nothing touching or crossing the middle or the edges, and no grid lines, boxes, labels, or numbers.

**Cutting.** The cutter needs no vision model and no fixed coordinates:

1. It finds the artwork: pixels with alpha 24 or more. If under 5% of the image is clear (the model ignored transparency), it keys out the most common edge color instead, which also clears parts of the design in that exact color.
2. It finds the emptiest column and row in the middle 30% (35–65%) of the image, nearest the center on ties. Those are the cut lines.
3. It labels connected shapes (8-connected) and gives each shape whole to the quarter that holds most of it, so a design that pokes past a cut line isn't sliced.
4. A shape with at least 15% of itself on both sides of a line straddles it. If it's thin where it crosses (35% or less of its thickest point), it's two designs touching and is cut there; otherwise the quarters it covers come back `merged` and are refunded. A quarter with almost no art comes back `empty`.
5. Each design is cropped to its own artwork plus 2 px of soft edge and a **4 px clear margin** on every side, copying only pixels that belong to that design.

In tests, all 16 real grids cut cleanly into four (the nearest art sat 21–116 px from the middle), including solid color-block posters, which keep the clear space around each panel. Cutting takes about 1.4 s per grid. Unit tests: `tests/unit/gridCut.test.ts`.

**In the studio** (since 2026-10-02), each batch is one grid call (`imageGen.runBatch`). The four cut designs each get their own folder with copies, and the whole grid is kept at `grids/<sha256>/original.png` for checking cuts. A batch costs 2 credits, charged once. A quarter that comes back `merged` or `empty`, or a failed or blocked call, gives credits back: 1 for one or two missing designs, 2 for three or four (`convex/lib/studioRules.ts`); the batch line says "1 credit back". Cutting and storing take about 3 s after the image arrives (1.7 s to cut on Convex's servers, 1.3 s to store four designs with their copies); when Convex's servers were busy it took up to 16 s. In six studio batches on dev (words only, twice; a photo and a poster; a lion design as the style for a dragon; a remix; a photo and a pop-art portrait), all 24 designs cut cleanly and no credits came back. The ChatGPT path and `STUDIO_LAYOUT=single` still make four separate calls at 1 credit each.

## The studio: images and the style mixer

The studio has two inputs, and where an image is added decides its job:

- **Images** (numbered 1–8 above the prompt box) are what to work on: their people, words, characters, and layout. With no style in the mixer they keep their own look, so "Change the words to GROW WILD" just works.
- **The style mixer** (closed by default, below the prompt box) holds up to four styles, each with a 0–100 slider. Nothing joins the mix on its own: a member uploads a style image ("Upload a style image" opens a picker with their past style images first, then their other images, or upload from the computer), drops one on the mixer, adds an image's look with "+ Image 1", or picks "Use as style" on a design.
- **Naming a style in words works the same as the mixer.** With a photo as image 1 and a poster as image 2, "Reimagine image 1 in the style of image 2" builds exactly the prompt the mixer would: image 2 becomes a style at full strength, and because the request names it only for its look, its people and words stay out. Other ways of saying it count too: "image 2's style", "the same style as image 2", "make it look like image 2", "use image 2 as the style", "the second image", "the styles of images 2 and 3". If the mixer already has a slider on for that image, its value is used. "Keep image 1's look" and "not the style of image 1" don't make an image a style. GPT-6 Luna reads the request on the server before each grid batch (`convex/lib/roleReader.ts`, low reasoning, about 2.5 s; the four-call path uses the phrases) and decides, for each numbered image, whether the request wants what's in it, only its look, or both. It's told which images are in the style mixer, so "in the style" or "like the style" with no image named means the mixer's style. It also says whether the request asks to give people the style's hair (see the Keep step below). The phrases above (`namedStyles` in `convex/lib/prompts.ts`) decide when it can't answer. On 16 requests written to be tricky, Luna read 14 as intended, and the other two defensibly, where the phrases alone read 8: it caught "make her look like she belongs in the second picture", "draw the woman the way the poster draws people", "a dragon in this style", and "remix this with the colors of image 2", and left "swap the lion for my cat" and "put the woman into the picnic scene" as content. Each batch saves what was read, so its line shows a style named in words with the same thumbnails and shares as the mixer.
- **Limits.** Up to 8 numbered images and 4 styles. One call took 16 images in testing and kept every image's subject (see the tests below); each image adds about 0.7–1.3¢ per batch, depending on its size.

Sliders become shares: two styles at 100 are 50/50, 100 and 50 are 67/33, zero is off. Each row shows its real share.

The prompt placeholder follows the images: "Describe your design…" with none, "Change the words, colors, characters…" with one, and "Refer to them as image 1 and image 2…" with more. With two or more images, three examples sit under the box ("Draw image 1 in the style of image 2", "Use the colors of image 2", "Put the people from image 2 into image 1"); tapping one adds it to the request.

**Style names.** The mixer's rows are labeled Style 1 to Style 4, and with two or more the mixer says "In your request, call them style 1 and style 2." The request reader is told each mixer image's name and that those names point at the mixer. When a request names a style, the prompt tags that mixer image with it ("Image 3 (the request's style 2): …"), so "put style 2 on the lettering" reaches the right picture. Tested 2026-10-06 with four such requests, three reads each: 12 of 12 as intended, and the earlier 27 requests still read 79 of 81 as intended (the two misses were a timeout and one "a dragon in this style" read as content).

**Start from this.** Every finished design's menu, the viewer's main button, and its B key start a fresh prompt in the same session with that design as image 1: the request, the other images, and the mixer clear, and the design's shirt color comes along. "Add as an image" adds a design to the images already there.

**Shirt color.** The swatch beside the images previews designs on a shirt color. Only image 1 suggests one (the nearest shirt color to its own background), and only until the member picks a color; style images and later images never change it.

## Notes for every image

When an image first comes into the studio, `convex/imageNotes.ts` asks GPT-6 Luna for notes with `STYLE_NOTES_PROMPT`, and `userImages` stores them once per member and image (matched by SHA-256), so reusing an image costs nothing. Transparent images go to Luna on flat gray with a note saying so, since vision models read clear pixels as black. The notes have these parts:

- **Summary** and **Kind** (photo or art): the image's short name in prompts. Neither is shown in the studio (see "What stays on the server").
- **Subject and layout**, **Words** (every piece of text, most prominent first, with its exact spelling, role, position, size, and lettering), **People and characters** (who is in it and what makes each person recognizable from head to toe, build and height included, without naming anyone).
- **Technique**, **Color** (with hex codes), **Line and shading**, **Lettering** (the overall approach), **Figure drawing** (how the image draws people and animals from head to toe compared with real anatomy: how many heads tall, head size against the body, body shape and silhouette, neck, torso, limbs, hands, and feet, the head and face including ears, and posture, with numbers where possible; hair goes only in a closing "Hair:" line that describes the shape and texture of the hair shown, without its color, such as "tall sharp spikes standing straight up"), and ranked **Signature traits**, each written as a way of drawing that carries to any subject ("Ben-Day halftone dots in the shadows," not "a dotted yellow background"; "neon pink and cyan against heavy black outlines," not "pink hair").

The first group is content; the second is style. A person's likeness (their face, hair, and build) is content; the way an image draws people from head to toe (how tall and stretched, how big the head and ears) is style. Hair counts as likeness: people keep their own unless the request asks for the style's. A distinctive way of drawing people counts as one of the signature traits, so it carries over even when the style has a small share of the mix. A body part only the image's own subject has, such as a lion's mane, horns, or wings, never counts as a trait. Listed as "a voluminous pointed mane," it put a lion's mane on wolves drawn in the lion's style; without it, 12 of 12 wolves at medium quality had none. At high quality about half still take a mane-like ruff, which comes from the picture itself: removing the word from the prompt entirely didn't change that, and a sentence forbidding the style subject's body parts made it worse (2026-10-05). The prompt uses each half where it belongs.

**Published designs keep their notes.** When a design is published, `imageNotes.analyzeWork` writes notes for it once (or copies the creator's own notes for the same file) and keeps them on the work. Anyone who remixes it gets those notes the moment the design enters their studio, so a remix never waits on Luna. `bunx convex run imageNotes:backfillWorks` writes them for designs published earlier.

**Re-reading notes.** After the notes prompt changes, `bunx convex run images:reanalyzeAll` re-reads every member image, 200 per run and a second apart (run it again with the cursor it returns until it returns null). A re-read that fails keeps the image's earlier notes.

GPT-6 Luna read stylized lettering right in 9 of 9 tries and listed 16 separate pieces of text on a newspaper page; GPT-6 Sol and GPT-5.6 Terra cost about 20× more and misread the same lettering. Luna's one miss was an ornate blackletter masthead.

## How the prompt is built

`studioPrompt` in `convex/lib/prompts.ts` assembles the parts in this order; the creator's request comes last and wins any conflict:

1. **Task and rules**: one design on a transparent background, print-ready (or the grid rules).
2. **Attached images**: "Image 1: a smiling woman in a park", "Image 2: vintage picnic illustration (style only: use its look, never its subjects or words)". Images in the mixer that aren't numbered images are attached after them. "Style only" marks images added only in the mixer and numbered images the request names only for their look; a single image in the top row is never marked, so "Change the words" keeps its lion, people, and layout.
3. **Keep**: study the numbered images closely and keep their composition. With no style, keep their look and each person's likeness; if the request asks for a different style, draw everything that way and keep people recognizable within it. With a style: "keep the recognizable likeness of every person and animal in image 1, such as their hair, glasses, freckles, and smile, so someone who knows them would recognize them, while drawing them fully in the style, from head to toe: the style decides their proportions and shapes, such as how tall and stretched the body is and how big the head and ears are. Unless the request says otherwise, each person keeps their own hair color." (That last sentence was added on 2026-10-05, after the image test suite saw the pop-art style turn her copper hair pink in all four designs in 2 of 8 grids; with it, 6 of 6 grids kept her copper hair, and "with bright pink hair" still made it pink in 4 of 4.) The style's hair appears nowhere in the prompt unless the role reader says the request asks for it ("with the style's hair", "give her the cartoon's spiky hair"); then the style's "Hair:" line goes in, in full: "Give people the style's hair: tall, sharply pointed spikes…, in their own hair color." (The likeness tests below compared four wordings; the whole-figure test shows why hair works this way.)
4. **Notes on each numbered image**: all of them with no style; with a style, only its scene ("Subject and layout") and its words. The "People and characters" notes describe real faces and kept faces from taking on the style (see the tests below); the model keeps people recognizable from the image itself.
5. **Style mix**: one style "sets the whole look"; with several, the largest share leads (sets technique, line work, color, lettering, and figure drawing) and each smaller share must be "clearly visible in every design, not a faint hint" through its top two or three signature traits. Since 2026-10-05 each smaller share gets a part of every design instead: on the main subject (its coloring and shading), around it (backdrop, frame, ornaments, and print texture), the lettering, or small accents. Since 2026-10-06 GPT-6 Luna picks each part from the style's notes and the request (`convex/lib/styleParts.ts`, about 2 s), so a style known for its lettering goes on the lettering and takes it from the leader; without an answer, parts go in size order (subject, around, lettering, accents). Styles within 10 points share the lead. The leading style's figure drawing, head to toe, is stated as a requirement, including for people from photos. Each batch keeps what every style did (`batches.styleJobs`, from `styleJobs` in `convex/lib/prompts.ts`, the same function the prompt is written from), and the studio's batch line shows it beside each share on wider screens: "67% leads · 33% lettering" (subject, backdrop, lettering, or accents), with a longer description on hover.
6. **Style definitions**: the style sections of each style's notes.
7. **Request**: the creator's words, with any words in capitals or quotes spelled letter by letter, and new words replacing old ones.

**Remixes.** A remix keeps the published design's look, words and all, and changes only what's asked. With a style in the mixer it keeps the design's composition, subjects, words, and likeness, and draws all of it in the style, lettering and figure proportions included; people keep their own hair unless the request asks for the style's. **Word changes** from the remixable words' boxes go in as their own block: each changed piece spelled letter for letter in its place (and its size, unless the new words are much longer, when the model may set them smaller or over more lines), each emptied box's piece removed, every other piece listed to keep, and a rule that all four designs show the new words. A box takes up to 80 characters; anything else, like added words, goes in the request, which a remix can always use. The design's own Words notes stay out of a word remix, because they list the old words.

**Words on every design.** A request's words go on all four designs of a grid: with a style and "vary their composition," the model left GOOD DAY off three of four designs until the prompt said every design shows them (image test suite, mix-50-50, 2026-10-05).

**The spelling check.** When a batch asks for words (in capitals or quotes, or a remix's new words), each of its designs is read back letter for letter by Gemini 3.1 Pro at low thinking, the image test suite's word reader (`convex/spelling.ts`, `convex/spellingCheck.ts`, `convex/lib/wordReader.ts`; about 0.3¢ and 7 to 18 seconds a design, which the studio absorbs). An asked-for word drawn a letter or two off is saved on the design (`convex/lib/spelling.ts`: one letter in a four-letter word, two in five to seven letters, about a third beyond). The studio marks the design **Typo?**, the large view says "It reads TRROSH where you asked for TRASH," and **Fix the spelling** (there, in the ⋯ menu, and in the publish dialog) starts a fresh request on the design: "TRASH is drawn wrong; it reads trroh. Redraw that word from scratch with exactly its 5 letters, in the same lettering style, size, colors, and place, without reusing its current letter shapes. Keep everything else exactly as in image 1." The right word is in capitals, so it's spelled out for the model and checked again; the misreading is in lowercase, so the check doesn't count it as asked for. A plainer "fix the lettering, keep everything else" copied the wrong letters back, since the design's notes read its lettering as the intended word (the image test suite's `words-fix-spelling` case and the [notebook](style-mixing.md) have the three wordings tried). Publishing still works. Words of three letters or fewer aren't checked, and neither is a word the design doesn't show at all, since a word in capitals can name a style rather than ask for lettering. OpenAI's vision models can't do this job: they read what a design probably meant, TRRSH as TRASH (`convex/lib/models.ts`, `WORD_READER_MODEL`).

**Remixable parts.** Beside its words, a design can let remixes change its characters, people, and groups (`convex/lib/remixParts.ts`, `convex/remixParts.ts`). A **character** ("The lion") takes words to swap it for, or a photo; a **person** ("Santa") takes a photo of who should be them, and the creator picks what happens without one: keep the original, leave them out, or ask for a photo; a **group** ("Elves") takes one photo per member, up to the creator's limit (eight at most), so a family of five can be five elves. GPT-6 Luna proposes the parts from the design's notes (`convex/lib/partsReader.ts`); the creator switches them on, renames them, sets their rules, adds a note for the prompt ("pointed green hats"), or adds a part by describing it ("let people add their family as elves"). Creators set this up in the studio with **Make it remixable** on a design, test it with **Try it as a remix**, which opens the exact form a remixer gets with the design as image 1, and publishing carries the setup to the work; the work page and the publish reveal edit it after. Works published without a setup get parts proposed when their notes are written (`remixPartsActions.backfillWorks` covers older works).

Code turns filled-in parts into their own prompt block: each photo is numbered after the remixer's images and marked "for Santa: use only the likeness of who or what is in it, never its background", and only its "People and characters" notes go in. A person "becomes image 1's Santa: same place, pose, and outfit, drawn the way image 1 draws people, but with their own face, hair, skin tone, glasses, age, and expression from their photo"; a group is "exactly 4 elves (image 1 shows 3), no more and no fewer, one for each photo: 1: the person in image 4; …"; a count check closes the block ("1 Santa, 1 Mrs. Claus, 4 elves, and every photo appears exactly once"). The server checks every part against the stored rules (`checkPartChanges`), never the browser's copy. A remix that changed only its words and parts publishes as a variation, and the comparison is told which parts the creator opened ("Elves (any number of them, drawn from photos, and the room they take)"), so five elves where there were three stays a variation.

**Tested 2026-10-06** with a Santa, Mrs. Claus, and three elves design and six made-up family photos (`.tmp/family/`), GPT Image 2.5: the first wording described each role with the original's own looks ("an elderly woman with curled white hair, spectacles") and kept the original Mrs. Claus in all four designs, and "three elves" beside "exactly 4" gave three elves in all four. Naming people and groups by role only, with their looks coming from their photos, fixed both: in 8 of 8 designs at medium quality Santa had the dad's beard and glasses, Mrs. Claus the mom's red curls and freckles, and there were exactly four elves with the girl's braids, the boy, the toddler's curls, and grandma's white hair and glasses. With Santa kept, Mrs. Claus left out, and six elves (the whole family), 8 of 8 designs kept the original Santa, had no Mrs. Claus, and drew six recognizable elves, arranged in two rows. Each grid took about a minute with seven input images and cost about 9¢ at medium. Sheets: `.tmp/santa/try1-sheet.png` (first wording), `.tmp/santa/v2/sheet.png`, `.tmp/santa/v3/sheet.png`.

**Keep it just for you.** The publish dialog asks who a design is for. **Share with the world** gives it a CR number, a spot in the feed, and lets anyone order or remix it. **Keep it just for you** gives it no public number (an internal one in family 0, which no CR string can name), keeps its art at the design's own unguessable address, and skips the feed, notifications, family, onchain record, model photo, and shop listing; every public query reads only status "published", and a kept work's status is "private". A kept remix keeps its parent, so the original's creator still gets credit. It opens at `/keep/<id>` for its creator alone, and **Share with the world** there gives it the next public number (a variation of its original) and runs the public steps.

**Variation or fork.** A remix that changed only its original's remixable words publishes as a variation. Anything more (a request in words, a style, more images, or other art as image 1) is compared with the original when its creator opens the publish dialog: GPT-6 Luna looks at both images (`convex/lib/remixJudge.ts`, `convex/remixCheck.ts`) and answers whether the remix is still the same design or a new one. A design is its look and its layout (Jon's rule, 2026-10-05): a remix that keeps the original's drawing technique, line work, texture, lettering style, and layout is a variation even when its main character is swapped (a lion for a wolf), its words change or move to fit, it's recolored, or it gets a new background; a remix redrawn in a clearly different style or medium (pixel art, pop art, a pencil sketch), even with the same layout and subject, or with its artwork rebuilt into a different composition, is a new design. Changed words and swapped subjects never make a fork, and a close call is a variation. Only a remix that reads as a new design can be published as a fork, which the dialog suggests, and the server refuses anything else (`publish.quick`). If the comparison fails three times, the remixer chooses. On dev it took 6 to 8 seconds (about 18 when 45 ran at once) and cost about 0.03¢. With the rule above, on 15 fixture pairs, three tries each, it answered as expected 45 of 45 times: word changes, added words, a new background, a lion turned dragon, and the mushrooms swapped for a cactus were variations; the design redrawn as pixel art, a photo redrawn as a cartoon or a 70s poster, and an unrelated design were forks. It also called all 72 word-remix designs from earlier suite runs variations (lettering moved to fit longer or removed words included) and all 24 photos restyled as pop art or a cartoon forks. A pencil-sketch lion under hand-lettered WILD AT HEART, remixed with "Change the lion to a wolf," came back as four pencil-sketch wolves under the same words, and all four read as variations. A raccoon design restyled with pop art or a 70s poster, keeping its layout and lettering, can go either way, depending on how far the redraw moved. Before the rule (2026-10-05, earlier), a swapped subject read as a fork and the pixel-art redraw as a variation. ## What stays on the server

Nothing the vision model writes about an image, and no prompt, reaches the browser. The browser sends image IDs, slider values, and the creator's own words. `imageGen.runTile`, an internal Convex action, builds the prompt and sends it straight to the image model, and no prompt is stored. A member can still guess a style by looking at the images, but the notes and our wording are never shown.

- `images.status` and `images.library` return an image's URL and whether its notes are pending, ready, or failed, never the notes, summary, or kind. The studio names a style by its row and where it came from ("Style 1 · image 1's look", "Style 2 · style image") and shows a mix as thumbnails with their shares.
- A failed design shows one of a few fixed messages (`publicTileError` in `convex/lib/imageErrors.ts`). The raw error stays in `generations.error`, because a provider's error text, or the model's own reply on the ChatGPT path, can quote the prompt.
- Every public function declares the fields it returns, and Convex refuses to return a field that isn't declared, so a new field on `userImages` can't reach the browser by accident.
- No browser code imports prompt code. `tests/unit/clientBoundary.test.ts` follows every import from `src/` and fails if it reaches a `convex/` file outside a short list of files that are safe in the browser (`_generated/api.js`, `lib/authz.ts`, `lib/colors.ts`, `lib/username.ts`). The shop page's shirt-color names moved from `prompts.ts` to `lib/colors.ts` for this.
- The style library from Style Of will follow the same rule: its style definitions live in Convex, public queries return a style's name, category, and preview images, and a member's pick reaches the server as an ID and a slider value. Keep the definitions out of this repository.
- Whenever this repository is public (it was for the September 29 judging; it's private now), anyone can read the prompt templates in `convex/lib/prompts.ts`, this README, and the experiment scripts on GitHub. The notes for each image and the prompts built from them live only in the database.

## Storage and sizes

Every image is kept in up to four versions:

| Version | Size | Format | Kept in | Used for |
|---|---|---|---|---|
| Original | as made: 1024×1536 designs, ~650–900 px wide grid cuts, 1024×1024 model photos, uploads up to 1024 px | PNG (uploads keep JPEG or WebP) | public bucket | Download, Open full size, publishing, sending to the image models, the viewer and shop page once loaded |
| Medium | fits inside 1200 px, never enlarged | WebP, quality 82 | public bucket | studio tiles, the feed, shop pages, the first frame of the viewer |
| Thumbnail | fits inside 400 px | WebP, quality 78 | public bucket | session cards, image and style chips, the image tray, the style picker |
| Print upscale | Topaz 4× (see below) | PNG | public bucket, under its own code (Print Studio) | the printer's file and the owner's spot check |

Both copies keep transparency (alpha quality 90). On dev's 52 images, the originals total 136.6 MB, the mediums 14.5 MB, and the thumbnails 2.2 MB, and all 47 transparent designs stayed transparent. The blank studio's session cards now load 28 thumbnails, about 1.2 MB, where they used to load the same number of full PNGs.

**Where they live.** Each environment has one public R2 bucket, `cultremix-dev-public` and `cultremix-prod-public`, served from its r2.dev address with a one-year immutable cache. It's organized the way the product is, and everything that isn't public on a page carries a random code in its path (`convex/lib/sizes.ts`):

```
members/<member>/uploads/<date>-<code>/                     an upload: original.jpg (or png, webp), medium.webp, thumb.webp
members/<member>/sessions/<date>-<session>/batch-01/
    grid-<code>.png                                         the 2x2 grid the batch's four designs were cut from
    design-1-<code>/ ... design-4-<code>/                   each design: original.png, medium.webp, thumb.webp
works/<family>/<expression>/                                a published work: original.png, medium.webp, thumb.webp
works/<family>/<expression>/photos/<n>/                     its model photos (a reshoot takes the next n)
works/<family>/<expression>/print-<code>/print.png          its print file
```

**Unguessable links.** `<code>` is 26 lowercase base32 characters, 128 bits from the platform's cryptographic random source (`convex/lib/codes.ts`), made when the file is saved. Every upload, design, grid, and print file has its own code, so a link gives nothing away about any other file: someone with one design's link can't reach the other designs in its batch, the batch's grid, the member's uploads, or a work's print file. The bucket can't be listed through its public address (the root, folder paths, and S3-style list requests all return 404), so the exact link is the only way to a file. Studio links appear only in the member's own studio and public pages show only `works/` files, which are public anyway, so those paths stay readable (`works/101/001/original.png`). If a link ever leaked, moving that one folder to a new code would retire it.

**Folder names.** `<member>` and `<session>` are Convex IDs, and `<date>` is the Pacific date the session started or the upload arrived, so folders list in order in the Cloudflare dashboard. Batches are numbered within their session (`batches.number`, counted by `creativeSessions.batchCount`). Publishing copies the design and its two copies into `works/<family>/<expression>/`; the session keeps its own copy, so its history stays complete. A file's SHA-256 lives in the database (`generations.sha256`, `userImages.sha256`, and `works.contentHash`, the fingerprint the shop page shows and the registry records). The same photo uploaded twice by one member is stored once (`images.findUpload` matches the hash); two members' copies stay in their own folders.

Without R2 keys, `IMAGE_STORE=convex` keeps images in Convex file storage (`cvx:<id>` keys, served by the `/img/` route). Before launch, the production bucket should get a custom domain (such as `img.cultremix.com`, in the bucket's Settings under Custom Domains): Cloudflare rate-limits r2.dev addresses (heavy traffic gets 429 Too Many Requests and slower downloads) and recommends them only for development, while a custom domain adds Cloudflare's cache (https://developers.cloudflare.com/r2/buckets/public-buckets/). Keys are stored without the address, so the switch is one change to `R2_PUBLIC_URL`, and the bucket's CORS rules carry over.

**No content credentials.** The image model writes a C2PA content credential into every PNG it returns (a `caBX` chunk). CultRemix doesn't keep it. `convex/lib/pngMeta.ts` removes that chunk, along with any text, EXIF, and timestamp chunks, from the model's output before anything hashes, cuts, or stores it; the pixel data and the chunks that change how pixels look (transparency, gamma, color space, density) are kept byte for byte. Designs cut from a grid were already clean, since the cutter encodes them from pixels, and so were uploads: the browser redraws each one on a canvas before sending it, which also drops EXIF and any location data. Hashes are taken after the metadata is removed, so a published work's fingerprint on its shop page is the SHA-256 of its file as stored.

**How the copies are made.** `convex/lib/storage.ts` resizes with sharp, which Convex installs on its Node runtime (`convex.json` lists it). A new design or model photo is uploaded at the same time as its two copies are made and uploaded, and the tile appears only when all three are stored, so no page loads the PNG first. With warm servers that takes 0.65–1.1 s per design (the original's upload is about 0.4 s of it); the first designs after a deploy took 2.3–2.6 s. Uploads get their copies right after they're stored; a published design is the same file, so it already has them. The `imageSizes` table maps an original's key to its copies, and queries return `url` (the original) with `thumbUrl` and `mediumUrl`, which fall back to the original until the copies exist. Saving to R2 is one direct upload per file: the R2 component's own `store()` adds a lookup and a separate action that records each object, which this app never reads, and that doubled the time to save a design.

**Older images.** Three jobs bring older images into this layout; each can run again. `bunx convex run sizing:organize` (add `--prod` for production) first numbers every session's batches in the order they were made, then moves designs into their session's batch folders, uploads into each member's uploads folder (one member's file never lands in another's), each grid beside its designs, model photos into their work's `photos/1/`, and published art into `works/`. Designs, model photos, grids, and published art lose the image model's metadata on the way. Files come from Convex storage or any older R2 layout (one folder per SHA-256 under `designs/`, `uploads/`, and `grids/`; flat `gen/`, `art/`, `photo/`, and `inspo/` files with copies under `sizes/`). Each row is patched as soon as its file is in place, and moves are recorded in `storageMoves` so a file several rows share is copied once; a published work's art that a remix used as its image follows the work. A second run reports moved 0. `bunx convex run sizing:backfill` then makes any copies still missing. `bunx convex run sizing:cleanup` deletes everything left in the older layouts and all of Convex file storage; it refuses, deleting nothing, while any table still points outside the current layout, and never deletes a file a table uses. On dev (Oct 3), organize moved 117 items with no failures, a second run moved nothing, the backfill found every copy in place, and new batches and publishes then saved straight into the new layout.

**Print files.** A work's print file goes in its work's folder under its own code (`works/<family>/<expression>/print-<code>/print.png`, built in the Print Studio) and is never shown on a page; the printer and the owner's spot check get its link.

## Shirt products and colors

**Products.** `/admin/products` searches Printful's public catalog of shirts, tanks, sweatshirts, and hoodies (no Printful account needed: `GET https://api.printful.com/products` and `/products/<id>`), adds a product with every color it comes in, grouped from its variants (name, Printful's swatch hex, variant ids by size, a photo of the blank, and whether it's in stock), and lets an admin pick which colors are offered and which product is the active shirt (`convex/merch.ts`, table `merchProducts`). Added 2026-10-06: the Comfort Colors 1717 came in with all 50 of its colors; the 12 launch colors it shares started picked. **Refresh from Printful** rereads a product and keeps the picked colors.

**The palette.** The active shirt's offered colors are what the studio previews designs on and what publishing offers and checks (`merch.palette`, `activePalette`); with no active shirt, the launch colors in `convex/lib/garments.ts` stand in. A color's key comes from its catalog name ("True Navy" is `true-navy`), so works published with the launch colors keep their names. Old works show their colors from any product that had them (`colorLookup`).

**The studio's shirt color.** The swatch beside the images opens the palette. Only image 1 suggests a color, as the nearest shirt color to its own background; style images and later images never change it, and neither does anything once the member picks one. Designs show on the chosen color in the studio, the viewer, and the publish dialog.

**A version for a color.** The publish dialog marks colors a design gets lost or faint on (the contrast check), and offers **Make a version for Moss** for up to three of them. It starts a new prompt in the same session with the design as image 1 and the shirt set to that color: "keep exactly the same design, words, layout, and drawing, and only recolor or outline the parts that would get lost on moss … Add nothing new." Tested 2026-10-06 on a gray pencil-sketch wolf: an earlier wording ("keep the same design, words, and layout") read clearly on moss but added mountains, pines, feathers, or a moon behind three of four; this one kept the wolf and words in four of four and changed only their colors, warm browns and darker outlines.

## Upscaling for print

fal's Topaz Transparent (`topaz/upscale/image/transparent`, https://fal.ai/models/topaz/upscale/image/transparent) always enlarges 4× and keeps the alpha channel, with PNG output. It costs $0.08 per started 24 megapixels of output, so any grid design (about 3,200×3,600 after upscaling, roughly 12 MP) is 8¢, and a 1024×1536 single design (about 25 MP) is 16¢.

On seven grid designs: transparency was kept every time (clear areas stayed 100% clear, alpha matched 99.99–100% when shrunk back), colors stayed within 1.5–6.6 of 255, no dark rims appeared at edges, and lettering came out sharper than a plain enlargement. Topaz Precision returned no alpha at all, so it can't be the fallback. The image model paints "solid" areas at alpha 240–254, so the print file rounds those up to 255.

Plan: upscale only when someone orders a print, right after payment, using the design's pre-upscale original. Upscaled images are never sent back to the image models. An automatic check compares the upscale with the original (transparency kept, colors close, no haze); a design that fails gets one retry, then waits for the owner. A side-by-side viewer of the print file for spot checks is at `.tmp/flow/upscale/` (served from `screen -S cr-screens`).

| Full-front file | 2,250 × 2,700 px at 150 DPI; 4,500 × 5,400 px at 300 | 4,500 × 5,400 px |
| File | PNG preferred (transparency), sRGB IEC61966-2.1, up to 200 MB and 20,000 × 20,000 px | Transparent sRGB PNG, up to 100 MB |

Sources: Printful's DTG guide (https://www.printful.com/creating-dtg-file) and help center (https://help.printful.com/hc/en-us/articles/50264010605457-What-is-DPI-resolution-and-actual-print-file-size, https://help.printful.com/hc/en-us/articles/50264397552657-How-is-my-design-scaled-for-different-garment-sizes, https://help.printful.com/hc/en-us/articles/50264019148177-How-should-I-prepare-my-print-file-for-the-best-results); Printify's help center (https://help.printify.com/hc/en-us/articles/4483601892497-What-dimensions-should-my-design-be, https://help.printify.com/hc/en-us/articles/4483617936657-What-type-of-print-files-does-Printify-require). Printify also notes that labeling a file 300 DPI adds no detail.

What our designs reach (the plan's print check: 150 DPI passes, 200 is great):

| Design | Width | 10 in print | 12 in print | 15 in print |
|---|---|---|---|---|
| Grid design as generated | ~650–900 px | 66–90 DPI | 55–75 DPI | 44–60 DPI |
| Single 1024×1536 design | 1,024 px | 102 DPI | 85 DPI | 68 DPI |
| Grid design after Topaz 4× | 2,628–3,256 px | 263–326 DPI | 219–271 DPI | 175–217 DPI |

So every design needs the upscale for a full-front print, and after it a 15-inch print sits around Printful's 150 minimum to the 200 mark, and 12 inches is comfortably "great." Shrunk to 11.5 inches on small sizes it's about 229–283 DPI.
