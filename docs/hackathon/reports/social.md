## How it maps to the plan

1. **Tables and publish event.** Done. There are three tables, plus two count tables so pages never count rows when they read. `markPublished` writes exactly one event; the test checks this.
2. **Idempotent follow and heart.** Done. `setFollow` and `setHeart` take the desired state (`follow: true/false`), so repeating a call or double-tapping changes nothing. You can't follow yourself; the server rejects it and the button hides. Counts change only when a row is actually inserted or deleted, in the same transaction. Both buttons appear on profiles, work pages, and feed rows. Signed out, they go to sign-in and come back.
3. **Profiles at `/u/<username>`.** Done, with everything listed above. Usernames link to profiles everywhere a creator is shown: feed rows, work pages, remix grids, and the header menu.
4. **Home feed with Latest and Following.** Done. Following is fan-out on read: it takes the latest 200 accounts the viewer follows, reads each one's newest events after the cursor, and merges them newest first. Signed out, Following returns an empty page and the tab is hidden.
5. **Pagination on every public list.** Done for home Latest and Following, profile Works and Remixes, and the work page's remixes. All of them use `.paginate()` on indexes, except Following, which uses its own cursor over per-account index reads. All of them use the same hook and the same LoadMore. The first page is prefetched during SSR. Grids use thumb-size images and feed rows use medium.
6. **Tests.** Done; details below.

## Decisions

- **Desired-state mutations** (`follow: boolean`, `heart: boolean`) instead of toggles, so retries and double taps are harmless.
- **Count tables instead of fields on `users` and `works`.** They don't touch other areas' tables, and the counts can't drift: each one changes only when its row is inserted or deleted.
- **Events carry the work's publish time** (`createdAt = publishedAt`), so backfilled events sort correctly. They also carry `shelf`, so a profile's Works and Remixes tabs each read one index range.
- **Following cursor** is `createdAt:creationTime`, which is unique and stable. An unreadable cursor returns an empty, finished page, and the client starts over from the top.
- **Remixes are oldest first** on the work page, so they read in CR number order. Latest and profiles are newest first.
- **One paging hook built on react-query**, not Convex's `usePaginatedQuery`. It works with `@convex-dev/react-query` and SSR, and pinning `endCursor` keeps live pages from overlapping or leaving gaps.
- I left `docs/hackathon/log.md` alone so parallel branches don't conflict; this report is the record.

## What is stubbed or limited

- **Follower and following lists.** The counts show, but you can't open them as lists yet.
- **Short pages are possible.** Profile shelves and remix pages skip withdrawn works after reading a page, so a page can come back short or even empty while more remain. The UI handles this by loading the next page. If withdrawals become common, add a status to the index.
- **No notifications.** Following someone or hearting their work doesn't notify them.
- **Avatars** use `users.image` when set. There's no avatar upload.
- **The CR number wraps on phones on the work page.** The existing `text-[20vw]` on `/cr/$cr` breaks "CR 125-001" across two lines at 390px. That predates this branch and I didn't restyle it. The fix is a smaller size on phones plus `whitespace-nowrap`.
