## How it maps to the plan

1. **Tables and publish event.** Done. There are three tables, plus two count tables so pages never count rows when they read. `markPublished` writes exactly one event; the test checks this.
2. **Idempotent follow and heart.** Done. `setFollow` and `setHeart` take the desired state (`follow: true/false`), so repeating a call or double-tapping changes nothing. You can't follow yourself; the server rejects it and the button hides. Counts change only when a row is actually inserted or deleted, in the same transaction. Both buttons appear on profiles, work pages, and feed rows. Signed out, they go to sign-in and come back.
3. **Profiles at `/u/<username>`.** Done, with everything listed above. Usernames link to profiles everywhere a creator is shown: feed rows, work pages, remix grids, and the header menu.
4. **Home feed with Latest and Following.** Done. Following is fan-out on read: it takes the latest 200 accounts the viewer follows, reads each one's newest events after the cursor, and merges them newest first. Signed out, Following returns an empty page and the tab is hidden.
5. **Pagination on every public list.** Done for home Latest and Following, profile Works and Remixes, and the work page's remixes. All of them use `.paginate()` on indexes, except Following, which uses its own cursor over per-account index reads. All of them use the same hook and the same LoadMore. The first page is prefetched during SSR. Grids use thumb-size images and feed rows use medium.
6. **Tests.** Done; details below.

## Decisions

- **Desired-state mutations** (`follow: boolean`, `heart: boolean`) instead of toggles, so retries and double taps are harmless.
- **Count tables instead of fields on `users` and `works`.** They don't touch other areas' tables, and the counts can't drift: each one changes only when its row is inserted or deleted.
- **Events carry the work's publish time** (`createdAt = publishedAt`), so backfilled events sort correctly. They also carry `shelf`, so a profile's Works and Remixes tabs each read one index range.
- **Following cursor** is `createdAt:creationTime`, which is unique and stable. An unreadable cursor returns an empty, finished page, and the client starts over from the top.
- **Remixes are oldest first** on the work page, so they read in CR number order. Latest and profiles are newest first.
- **One paging hook built on react-query**, not Convex's `usePaginatedQuery`. It works with `@convex-dev/react-query` and SSR, and pinning `endCursor` keeps live pages from overlapping or leaving gaps.
- I left `docs/hackathon/log.md` alone so parallel branches don't conflict; this report is the record.

## What is stubbed or limited

- **Follower and following lists.** Done in Round 2.
- **Short pages are possible.** Profile shelves and remix pages skip withdrawn works after reading a page, so a page can come back short or even empty while more remain. The UI handles this by loading the next page. If withdrawals become common, add a status to the index.
- **No notifications.** Following someone or hearting their work doesn't notify them.
- **Avatars** use `users.image` when set. There's no avatar upload.
- **The CR number wraps on phones on the work page.** The existing `text-[20vw]` on `/cr/$cr` breaks "CR 125-001" across two lines at 390px. That predates this branch and I didn't restyle it. The fix is a smaller size on phones plus `whitespace-nowrap`.

### Decisions

- **Why "Who's making things" has its own table.**
  - `creatorActivity` has one row per creator with `lastActiveAt` and an index on it, so the strip is one paged index read with no duplicates.
  - Paging `activityEvents` and removing duplicate creators would repeat creators across pages and come back short.
  - `recordPublishActivity` updates the row, and only ever moves the time forward. It runs on every publish and in the backfill.
  - Rerunning `activity:backfill` fills the table for creators who published earlier. It's safe to rerun, and now updates the table even when a work's event already exists.
- **The root no longer sets `og:image:width` and `og:image:height`.**
  - TanStack replaces meta tag by tag, so a work page would have inherited the site card's 1200×630 size with art that isn't that size.
  - The size tags are optional; crawlers read the size from the image.
  - The cost: Facebook may skip the image on the very first share of a page it has never seen.
- **Share cards come from the loader, not a new query.** The loader already fetched `feed.byCr` or `social.profile` for SSR, so it reads that result back from the query cache. A browser navigation never waits on it: if the data isn't cached yet, the tab shows the plain title, and crawlers always get the server render.
- **Medium art is `.webp`**, the size the storage branch makes for pages (up to 1200px). Most link previewers accept WebP, but not every one does, and I couldn't test real crawlers from here. If one matters and drops the image, a PNG or JPEG copy for previews would need the storage owner.
- **The share sheet only on touch screens.** Some desktop browsers also support Web Share, but the brief asks for copy link there.

**Notifications**
- **When they're written.** `notify()` (`convex/lib/notifications.ts`) runs in the same transaction as the action:
  - `social.setFollow`: "@bob followed you."
  - `social.setHeart`: "@bob hearted Night Market CR 101-001."
  - `publish.markPublished`, when a variation or fork of someone else's work is published: "@bob remixed Night Market CR 101-001 into CR 111-001." It notifies the parent's creator. Remixes are written at publish, not in the activity backfill, so old remixes don't flood anyone.
- **No self-notifications.** Nothing is written when the recipient is the actor, so hearting or remixing your own work is silent.
- **Collapsing.** A heart or follow from the same person (and, for hearts, on the same work) within 24 hours of an earlier one doesn't notify again, so heart, unheart, heart writes one row. After 24 hours it notifies again. Remixes and Backs never collapse.
- **Unread count.** `notificationState` keeps one row per member with `unread` and `lastReadAt`. Only a new, uncollapsed notification adds to it, so the bell reads one small row.
- **API**
  - `notifications.status`: `{ unread, lastReadAt }`, or zeros when signed out.
  - `notifications.list`: paginated, newest first, capped at 48. Each item has the actor's username and https avatar, the work (CR, title, thumbnail) while it's still published, and for a remix, the work it came from. Signed out, it returns an empty page.
  - `notifications.markAllRead`: sets unread to 0 and `lastReadAt` to now. It writes only when something is unread.
- **Bell** (`src/components/social/NotificationBell.tsx`): in the header for signed-in members only, between Studio and the account menu. It shows a black badge with the count ("99+" past 99) and an aria-label like "Notifications, 3 new".
- **Page** (`src/routes/notifications.tsx`)
  - Members only (`requireAuthenticatedRoute`), 20 per page, using the same `usePagedQuery` and `LoadMore` pattern.
  - On open, it saves the previous `lastReadAt` and then calls `markAllRead`, so the badge clears and the newly arrived rows keep a "New" tag while you're on the page.
  - Each row shows the actor's avatar, one plain sentence, how long ago, and the work's thumbnail.
  - A row opens the work it's about. A follow, or a work that's since been withdrawn, opens the actor's profile.
  - Empty state: "Nothing yet. When someone follows you, hearts your work, or remixes it, you'll hear about it here."
- **The Backs hook.** `notifyBacked(ctx, { workId, backerId, at? })` in `convex/lib/notifications.ts`. Call it once per back from the mutation that records the back. It notifies the work's creator ("@x backed CR 101-001."), skips self-backs, and never collapses. The page already renders `kind: "back"`, and it's covered by a test.

**Trending**
- **Score.** Hearts plus 3 × remixes from other members, over the last 7 UTC days, today included. Ties go to the most recent attention.
- **How it stays bounded.** No request scans or counts anything.
  - Each heart or remix adds 1 to a per-work, per-day bucket (`workAttentionDays`) and to the work's running score (`trendingWorks`, indexed by `[score, lastAttentionAt]`), in the same transaction.
  - Unhearting takes the heart back off, but only if its day is still in the window.
  - `feed.trending` reads one page of that index, descending, and builds items with the same `publishedItems` helper as Latest, so unpublished works drop out.
  - An hourly cron (`trending.expire`, at :03) takes buckets that have left the window off their works' scores and deletes them, 200 at a time. If there are more, it schedules itself again.
  - Rows at score 0 are deleted.
- **Home tabs.** Latest, Trending, and Following, with Following for members only. Signed-out visitors now see the tabs too, with Latest and Trending.
  - `/?tab=trending` is prefetched on the server like the other tabs.
  - Scores move while you scroll, so the list shows each work once.
  - Empty state: "Nothing trending this week yet. Heart or remix something you love." with a link to Latest.
- **`trending.rebuild`** (internal) clears the Trending tables and replays the last week of hearts (via a new `hearts.by_created` index) and published remixes. It's safe to rerun.

### Decisions

- **Counters plus a cron, not an hourly rollup.** Trending updates the moment someone hearts, and the cron only removes days that have aged out. An hourly recompute would have to read every heart in the week on each run.
- **Remixes are weighted 3×.** A remix takes much more effort than a heart. The weight is one constant, `REMIX_WEIGHT` in `convex/lib/trending.ts`.
- **Self-attention doesn't count** toward Trending or notifications, so no one can boost their own work.
- **Notifications stay when the action is undone.** An unheart or unfollow leaves the notification in place; it did happen, and deleting it would make the count jump around. Collapsing stops the same person flooding you by toggling.
- **The unread count is a counter, not a count of rows**, so the bell is one tiny read on every page.
